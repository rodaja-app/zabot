# ZaBot backend

Backend NestJS do ZaBot. Arquitetura completa, plano de etapas e decisões de produto estão em `../README.md` (raiz do projeto) — este arquivo cobre só o "como rodar" e o que já existe.

## Etapa 9 — Fundação

O que existe até aqui, tudo já testável isoladamente:

- **Contexto de requisição** (`src/common/context`): `AsyncLocalStorage` que carrega `requestId`/`sessionId`/`campaignId`/`contactId`/`userId` por toda a vida da requisição, sem precisar repassar isso manualmente em cada log.
- **Categorização central de erro** (`src/common/errors`): todo erro do sistema (proxy, rede, número inválido, rate limit, autenticação, validação, banco, entrega não confirmada, desconhecido) passa por `categorizeError()`. É o único lugar que decide "por que isso quebrou".
- **Filtro global de exceção da API** (`src/common/filters/all-exceptions.filter.ts`): captura literalmente qualquer erro de qualquer rota, loga estruturado (com stack e causa real) e responde JSON consistente.
- **Log estruturado** (`src/common/logging`): Pino com contexto automático em toda linha + Sentry condicional (erros 5xx) + `ConnectionEventLoggerService`, ponto único que as etapas de sessão/proxy/envio (11, 12, 15) vão usar para logar cada transição de conexão e cada transição de ACK de mensagem.
- **Filas** (`src/queue`): conexão Redis compartilhada + `attachQueueFailureLogging()`, ponto único de captura de erro de fila (BullMQ `QueueEvents`) que as próximas etapas plugam ao criar cada fila.
- **Prisma** (`src/prisma`): client único, com erros/warnings do próprio Prisma redirecionados para o log central.
- **Health check** (`src/health`): `GET /health` verifica Postgres e Redis de verdade (não só "processo de pé"). Usado pelo Railway no deploy.

## Etapa 10 — Autenticação e usuários

- **Modelos** (`prisma/schema.prisma`): `User`, `VerificationCode`, `RefreshToken`. `User` propositalmente **sem RLS** (login/cadastro não têm contexto de tenant ainda — ver comentário no schema); RLS de verdade começa na etapa 11 com as primeiras tabelas pertencentes a um usuário, usando `PrismaService.withTenantContext()`.
- **Senha**: hash com argon2id (`src/common/security/password.service.ts`).
- **Código de verificação**: 6 dígitos, hash sha256, expira em 15 min, máximo 5 tentativas (`src/common/security/verification-code.service.ts`).
- **Email**: `EmailProvider` trocável por injeção de dependência (`src/email`) — SMTP de verdade (nodemailer) se `SMTP_HOST` estiver definido no `.env`, senão cai num provedor que só loga o email (dev local sem SMTP configurado).
- **JWT**: access token curto (15 min) + refresh token rotativo (30 dias) com detecção de reuso — reapresentar um refresh token já rotacionado/revogado revoga a família inteira (indício de token roubado). Ver `src/auth/auth.service.ts`.
- **Rotas** (`src/auth/auth.controller.ts`), mapeadas 1:1 com `lib/data/auth_repository.dart` do front: `POST /auth/register`, `POST /auth/resend-code`, `POST /auth/confirm-code`, `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, `DELETE /auth/account` (protegida por JWT). Rate limiting mais apertado nas rotas sensíveis via `@Throttle()`, limite global mais generoso nas demais (`ThrottlerModule` em `app.module.ts`).
- Decisão de design registrada no código (`auth.service.ts`): login rejeita conta ainda não confirmada por email — o mock do front não modelava esse estado, mas deixar logar sem confirmar seria menos robusto.

## Etapa 11 — Sessões WhatsApp

- **Modelos** (`prisma/schema.prisma`): `Session` (1:1 por usuário — o front só tem uma tela de conexão) e `SessionAuthKey` (credenciais/chaves do protocolo Signal do Baileys, uma linha por chave). **Primeiras tabelas com RLS de verdade** do projeto — política em `prisma/rls/001_sessions_rls.sql`, aplicada manualmente após cada `prisma migrate dev` que mexer nelas:
  ```bash
  npx prisma migrate dev
  npx prisma db execute --file prisma/rls/001_sessions_rls.sql --schema prisma/schema.prisma
  ```
  Idempotente — pode rodar de novo sem problema. Todo acesso a `Session`/`SessionAuthKey` no código passa por `PrismaService.withTenantContext(userId, ...)`.
- **Criptografia em repouso**: `SessionAuthKey.ciphertext/iv/authTag` via AES-256-GCM (`src/common/security/session-crypto.service.ts`, chave em `SESSION_ENCRYPTION_KEY` — gerar com `openssl rand -hex 32`). Nunca se grava o auth state do Baileys em texto puro.
- **Auth state em banco** (`src/whatsapp/db-auth-state.ts`): substitui o `useMultiFileAuthState` padrão do Baileys (arquivos em disco) por `Session`/`SessionAuthKey` no Postgres — mesma forma/contrato (`{state, saveCreds}`), necessário para sobreviver a redeploy no Railway e para o modelo de sharding entre workers.
- **`WhatsAppProvider`** (`src/whatsapp/whatsapp-provider.interface.ts`): abstração entre o resto do backend e a lib que fala com o WhatsApp de verdade — troca de provedor futura (ex.: WhatsApp Cloud API oficial) é só uma outra implementação no mesmo token de DI. `BaileysWhatsAppProvider` (`baileys-whatsapp.provider.ts`) é a implementação de hoje sobre `@whiskeysockets/baileys`: gera QR (convertido para `data:image/png;base64,...` via `qrcode`) ou código de pareamento; reconecta automaticamente com backoff exponencial (1s a 30s) em quedas temporárias; distingue queda temporária de logout definitivo (`DisconnectReason.loggedOut`/`connectionReplaced`/`badSession`) e só nesse último caso apaga o auth state e exige QR/pareamento novo.
- **`SessionService`** (`session.service.ts`): orquestra tudo isso por usuário — cria/lê a `Session`, decide qual worker "é dono" da sessão (`Session.workerId`/`workerHeartbeatAt`, reivindicação condicional + heartbeat a cada 15s, expira em 45s), aciona o provider e persiste de volta no Postgres cada evento de `connectionUpdates$`. Retomada automática de sessão após o **próprio** processo reiniciar é deliberadamente fora do escopo desta etapa (o front sempre parte de um `connect()` explícito do usuário) — ver comentário no topo do arquivo.
- **Rotas** (`src/whatsapp/session.controller.ts`), mapeadas 1:1 com `ConnectionRepository` do front, todas atrás de `JwtAuthGuard`: `GET /whatsapp/session`, `GET /whatsapp/session/stats`, `POST /whatsapp/session/connect`, `POST /whatsapp/session/disconnect`, `PATCH /whatsapp/session/name`.
- **Tempo real** (`src/whatsapp/session.gateway.ts`): namespace WebSocket `/whatsapp` (socket.io), autenticado via `auth.token` no handshake (mesmo access token JWT do REST). Cada usuário entra numa room própria (`user:<id>`); eventos `session` (status/QR/pairing code/motivo de desconexão) e `stats` (contadores em tempo real — publicados via `SessionService.publishStats()`, que as etapas 13-15 vão chamar ao incrementar contatos/mensagens). Não existe no `ConnectionRepository` mock atual — é um canal net-new que a futura `ApiConnectionRepository` (etapa 18) consome sem exigir mudança nas telas. Roda com o adapter em memória padrão do socket.io (1 réplica); múltiplas réplicas exigem trocar por `@socket.io/redis-adapter` (não implementado ainda).
- **Sharding**: `WORKER_ID` (env, opcional) identifica esta instância no registro de sharding; sem ele, cada processo gera um uuid próprio ao subir — suficiente para 1 réplica.

## Etapa 12 — Proxy e resiliência de conexão

- **Modelo** (`prisma/schema.prisma`): `ProxyConfig`, 1:1 com `Session`. RLS em `prisma/rls/002_proxy_config_rls.sql`, mesmo procedimento manual da etapa 11:
  ```bash
  npx prisma db execute --file prisma/rls/002_proxy_config_rls.sql --schema prisma/schema.prisma
  ```
- **Sem rota/DTO para o usuário, de propósito**: a conta DataImpulse é uma só para toda a aplicação (`DATAIMPULSE_HOST/PORT/USERNAME/PASSWORD/PROTOCOL` no `.env`, ver `.env.example` e `env.validation.ts`) — "nenhum detalhe técnico de proxy é exposto ao usuário" (README raiz §4). O que isola cada sessão é a `stickyKey`, gerada e rotacionada só pelo backend; sem `DATAIMPULSE_HOST` no ambiente, as sessões conectam direto (mesma filosofia do `EmailProvider` log-only sem `SMTP_HOST`).
- **`ProxyConfigService`** (`src/whatsapp/proxy-config.service.ts`): cria/lê a `ProxyConfig` da sessão (credenciais cifradas em repouso com o mesmo `SessionCryptoService` da etapa 11), monta o `http.Agent` (`HttpsProxyAgent`/`SocksProxyAgent`, conforme `DATAIMPULSE_PROTOCOL`) com o username "enriquecido" pela sticky key (formato DataImpulse `LOGIN__sessid.<chave>`), testa conectividade real contra `https://web.whatsapp.com/` antes de abrir qualquer socket, e categoriza qualquer falha de proxy (nunca erro genérico): `proxy_host_nao_encontrado`, `proxy_recusou_conexao`, `proxy_conexao_resetada`, `proxy_timeout`, `proxy_autenticacao_falhou`, `proxy_erro_<code>`.
- **`BaileysWhatsAppProvider`** injeta o agent no `makeWASocket()` (`agent`/`fetchAgent`). Falha de proxy é tratada como falha de conexão: nunca abre o socket, entra no mesmo backoff exponencial de reconexão já existente (etapa 11), com o motivo categorizado do proxy.
- **Renovação de sticky session**: agendada com folga de 2 min antes do limite contratado (`DATAIMPULSE_STICKY_MINUTES`, padrão 30, máx. 120 — piso de segurança de 30s mesmo se configurado muito baixo). É um ciclo de reconexão controlado — nunca um logout: gira a `stickyKey` no banco, encerra o socket atual (`.end()`, sem `.logout()`, sem apagar auth state) e chama `startSession()` de novo, que abre um socket novo já com o IP renovado.

## Etapa 13 — Motor de contatos e normalização de números

- **Modelo** (`prisma/schema.prisma`): `Contact` (enum `ContactStatus`: `PENDENTE`/`VALIDO`/`INVALIDO`). RLS em `prisma/rls/003_contacts_rls.sql`, mesmo procedimento manual das etapas 11/12:
  ```bash
  npx prisma db execute --file prisma/rls/003_contacts_rls.sql --schema prisma/schema.prisma
  ```
  `rawPhone` nunca é sobrescrito (é o que volta se toda tentativa falhar); `normalizedPhone` só é preenchido quando um candidato bate de verdade no WhatsApp — a partir daí é o único usado (nunca mais re-testado, "cache do formato validado" do README raiz §5). `attempts`/`lastAttemptAt`/`failureReason`/`verificationLog` (array JSON append-only) implementam o registro auditável do §5 sem precisar de tabela separada.
- **`PhoneNumberService`** (`src/contacts/phone-number.service.ts`): canonicalização e geração de candidatos (README raiz §5, passos 1-2) — limpa o input, remove DDI 55/zero de tronco redundantes, e gera as variações com/sem o 9º dígito na ordem certa por DDD (tabela fixa dos DDDs onde a Anatel exige o 9º dígito no celular). Deliberadamente nunca tenta "corrigir" um DDD para outro — número com DDD errado vira `INVALIDO` categorizado, nunca um chute para a pessoa errada.
- **`WhatsAppProvider.checkNumbers(sessionId, candidates)`**: verificação em lote via `sock.onWhatsApp(...jids)` do Baileys (uma única chamada por contato, não uma por candidato). Como a API pode omitir do array de retorno os JIDs que não existem, o resultado é montado a partir do conjunto do que *veio* com `exists: true`, nunca por posição/ordem. Lança `SessionNotConnectedError` (categoria `sessao_desconectada`, HTTP 409) quando não há socket ativo para a sessão.
- **Fila `queue:validate-numbers`** (`src/contacts/validate-numbers.queue.ts` + `validate-numbers.worker.ts`, BullMQ manual — mesmo padrão da etapa 9, ainda em processo único): cada job é **uma passada completa** de verificação (gera até `CONTACT_MAX_VERIFICATION_ATTEMPTS` candidatos e testa todos em lote) — não existe retry sobre os mesmos candidatos, porque existência no WhatsApp não muda sozinha. A única causa de retry automático é a sessão estar desconectada (falha de infraestrutura transitória), tratada pelos próprios `attempts`/`backoff` exponencial da fila (5 tentativas, base 5s), sem consumir uma tentativa de verificação nem tocar no log além de registrar a causa. Worker é idempotente: contato já `VALIDO` nunca é re-testado.
- **`ContactsService`** (`src/contacts/contacts.service.ts`): espelha `ContactRepository` do front 1:1 (README raiz §13). `importContacts`/`addContact` criam linhas `PENDENTE` de forma síncrona (mesmo contrato do mock, resposta imediata) e enfileiram a verificação; `updateContact` só reabre verificação (reseta status/log/tentativas e reenfileira) quando o telefone de fato muda — editar só `customFields` não reprocessa nada. `Session.contactsImported` (`HomeStats` do front) é incrementado aqui, na entrada dos contatos — não no worker, que só acompanha o status de validação de cada um.
- **Rotas** (`src/contacts/contacts.controller.ts`), atrás de `JwtAuthGuard`, mapeadas 1:1 com o front: `GET /contacts`, `POST /contacts/import`, `POST /contacts`, `PATCH /contacts/:id`, `DELETE /contacts/:id`.

## Etapa 14 — Motor de mensagens e campanhas

- **Escopo desta etapa, deliberadamente limitado**: aqui só se **persiste** a campanha por completo — mensagens, mídia adotada, destinatários resolvidos e 1 `Envio` `PENDENTE` por par (destinatário × mensagem). Nenhuma linha é enfileirada para envio de verdade nem `Campaign.sentCount/failedCount` é tocado depois da criação. A etapa 15 (fila/rate-limit/anti-ban) é quem lê os `Envio`s `PENDENTE` já persistidos aqui, gera os jobs de envio de verdade e atualiza os contadores — separa "o que enviar" (aqui) de "quando/como enviar com segurança" (etapa 15), sem sobreposição de responsabilidade entre os dois módulos. Isso cobre a frase do README raiz §6 ("criação da campanha → gera 1 job por contato×mensagem na fila de envio") tratando criação e enfileiramento como etapas sequenciais donas de módulos diferentes.
- **Modelos** (`prisma/schema.prisma`): `Campaign`, `CampaignMessage`, `CampaignMedia`, `CampaignRecipient`, `Envio` (enums `CampaignMediaType`, `CampaignStatus`, `EnvioStatus`). RLS em `prisma/rls/004_campaigns_rls.sql`, mesmo procedimento manual das etapas 11-13:
  ```bash
  npx prisma db execute --file prisma/rls/004_campaigns_rls.sql --schema prisma/schema.prisma
  ```
  `CampaignRecipient.status` implementa o rollup por contato (não por linha de `Envio`) exigido pelo getter `Campaign.progress` do front (`progress = (sentCount + failedCount) / recipientCount`, sempre em unidade de contato): fica `PENDENTE` até que a etapa 15 decida — vira `ENVIADO` só quando **todos** os `Envio`s daquele contato tiverem sucesso, vira `FALHOU` (terminal, nunca reverte) assim que **qualquer** `Envio` daquele contato falhar em definitivo, mesmo com outras mensagens ainda pendentes para o mesmo contato. A regra em si é aplicada pela etapa 15; aqui só o estado inicial (`PENDENTE`) é gravado.
- **Duas extensões deliberadas além do contrato mockado** (`MessageRepository.createCampaign(messages, recipientCount, mediaType, mediaCount)` não tem parâmetro nenhum para bytes de arquivo nem para destinatários específicos):
  - `POST /campaigns/media` (multipart, fora do corpo JSON de `POST /campaigns`) faz upload de 1 arquivo e devolve `{id, mimeType, sizeBytes}`; o arquivo fica "órfão" (sem `campaignId`) até `POST /campaigns` adotá-lo via `mediaIds`. `mediaType`/`mediaCount` da campanha são sempre derivados da mídia adotada, nunca recebidos direto do cliente.
  - `POST /campaigns` aceita `recipientIds?: string[]` opcional — presente e não vazio envia só para esses contatos, omitido/vazio = "todos". **Em ambos os casos, sempre restrito a `Contact.status = VALIDO`**, mesmo que o front hoje permita selecionar qualquer contato importado sem filtrar por status (limitação do mock, não requisito a replicar num backend real).
  Os dois pontos são reconciliados com o contrato real do front na etapa 18 (integração final).
- **`PersonalizationService`** (`personalization.service.ts`): renderiza os tokens `{ID1}`..`{IDn}` de `Contact.customFields` no texto de cada mensagem. Função pura, sem I/O — usada de verdade pelo worker de envio da etapa 15 no momento de montar cada mensagem individual. Token sem correspondência (chave ausente ou valor vazio) fica literal no texto, nunca é apagado — apagar esconderia erro de digitação/import na hora de revisar a campanha.
- **Storage de mídia** (`media-storage-provider.interface.ts` + `s3-media-storage.provider.ts` + `local-disk-media-storage.provider.ts`, escolhido por factory em `campaigns.module.ts`, mesmo padrão de fallback do `EmailModule`): S3-compatível (`@aws-sdk/client-s3` — cobre AWS S3, Cloudflare R2 e MinIO, configurável via `S3_BUCKET`/`S3_REGION`/`S3_ENDPOINT`/`S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY`/`S3_FORCE_PATH_STYLE`) quando `S3_BUCKET` está definido, senão cai para disco local (`MEDIA_LOCAL_DIR`, padrão `./data/media`) — **só serve para dev local**, já que o filesystem do Railway não é persistente entre deploys. Falha de storage nunca vira erro genérico: categoria própria `ErrorCategory.ARMAZENAMENTO` (`MediaStorageError`), distinta de `REDE`, para diferenciar "S3 fora do ar" de "disco local sem espaço/permissão".
- **`MediaService`** (`media.service.ts`): valida (nunca transcodifica — o próprio Baileys/WhatsApp lida com o arquivo original na hora do envio, etapa 15) por categoria: `IMAGENS` (jpeg/png/webp, até 16MB), `AUDIO` (mpeg/ogg/mp4/aac/amr/wav, até 16MB), `DOCUMENTO` (qualquer mimetype — catch-all como o envio de documento real do WhatsApp, até 100MB). Mensagem de erro sempre cita o mimetype/tamanho recebido e o limite/whitelist da categoria.
- **`CampaignsService`** (`campaigns.service.ts`): `createCampaign` roda tudo dentro de 1 `withTenantContext` — valida mensagens (1 a 5, não vazias após trim), adota mídia (rejeita id inexistente/de outro usuário/já usado em outra campanha, e tipos mistos numa mesma campanha), resolve destinatários, cria `Campaign` (`status` já nasce `ENVIADA` se `recipientCount === 0`, já que não existe "pendente sem ninguém para enviar" no mock) e grava o produto cartesiano `CampaignMessage × CampaignRecipient` como `Envio`s. `clearHistory` espelha `clearHistory()` do front (apaga tudo — cascade cuida do resto).
- **Rotas** (`src/campaigns/campaigns.controller.ts`), atrás de `JwtAuthGuard`: `GET /campaigns`, `POST /campaigns`, `DELETE /campaigns/history`, `POST /campaigns/media` (multipart, campo `file` + campo de formulário `type`).

## Etapa 15 — Fila, envio e anti-ban

- **Escopo**: consome os `Envio`s `PENDENTE` já persistidos pela etapa 14 e faz o envio de verdade — 1 fila BullMQ por sessão WhatsApp (`queue:send-message:<sessionId>`), com janela de horário por fuso do contato, delay humano/jitter + rampa de aquecimento anti-ban, retries com backoff exponencial e uma trilha `queue:dead-letter` para falhas definitivas. `Campaign.sentCount/failedCount`/`CampaignRecipient.status` (deixados como estado inicial na etapa 14) só são tocados de verdade a partir daqui.
- **`WhatsAppProvider.sendMessage`** (`whatsapp-provider.interface.ts` + implementação em `baileys-whatsapp.provider.ts`): envia texto e/ou mídia (0+ anexos, todos do mesmo tipo — legenda só no primeiro item) para um único destinatário; lança `SessionNotConnectedError` (categoria `sessao_desconectada`) se a sessão não tiver socket ativo agora, tratado pelo processor como falha recuperável (mesmo padrão de `checkNumbers` da etapa 13).
- **`TimezoneService`** (`timezone.service.ts`): deriva o fuso do contato a partir do DDD do `normalizedPhone` (`55DDDassinante`) — sem depender de nenhum campo novo no schema. Offset fixo por DDD (Brasil não tem mais horário de verão desde o Decreto 9.958/2019): padrão UTC-3, com exceções documentadas no código para Acre/Rondônia/Amazonas/Roraima/Mato Grosso/Mato Grosso do Sul (UTC-4/-5). Janela de envio configurável via `SEND_WINDOW_START_HOUR`/`SEND_WINDOW_END_HOUR` (padrão 8h-20h local, limite superior exclusivo); `msUntilNextWindow` calcula o delay até o próximo início de janela, inclusive virada de dia.
- **`AntiBanService`** (`anti-ban.service.ts`): único mecanismo que resolve rate limit + jitter ao mesmo tempo — o worker roda com concorrência 1 por sessão, e antes de cada envio espera um delay sorteado uniformemente dentro de um bound que depende da idade da sessão (`Session.createdAt`, proxy de "há quanto tempo este número está registrado"): `SEND_WARMUP_MIN/MAX_DELAY_MS` (padrão 20-45s) enquanto a sessão tem menos de `SEND_WARMUP_DAYS` (padrão 3) de criada, `SEND_MATURE_MIN/MAX_DELAY_MS` (padrão 4-12s) depois disso.
- **`SendMessageQueueService`** (`send-message.queue.ts`, produtor): 1 `Queue` BullMQ por sessão, criada sob demanda. `enqueueCampaign(userId, campaignId)` lê os `Envio`s `PENDENTE` da campanha, enfileira 1 job por envio (`jobId = envioId`, idempotente contra chamada duplicada), soma a `Session.messagesPending` e publica via `SessionService.publishStats`; retorna o `sessionId` usado (ou `undefined` se não havia nada pendente) para o chamador acionar o worker. `reschedule()` reenfileira um envio com delay explícito quando cai fora da janela de horário, sem contar como tentativa nova.
- **`SendMessageProcessorService`** (`send-message-processor.service.ts`): a lógica de negócio de 1 tentativa de 1 `Envio`, isolada do BullMQ para ser testável direto — (1) idempotência (`Envio` que não está mais `PENDENTE` não faz nada); (2) fora da janela de horário do contato → reagenda via `SendMessageQueueService.reschedule` e retorna, sem contar tentativa; (3) delay anti-ban; (4) personalização (`PersonalizationService`, etapa 14) + mídia (só na mensagem de `order === 0` de cada destinatário — mídia é por campanha, não por mensagem); (5) `WhatsAppProvider.sendMessage` — sucesso chama `markSent` (marca `Envio` `ENVIADO`, recalcula `CampaignRecipient.status`, incrementa `Session.messagesSent`); falha de tentativa persiste `attempts`/`failureReason` categorizado e relança (quem decide retry/desistência é o BullMQ). `finalizeFailure()` — chamado só quando o BullMQ esgota as tentativas — faz a transição terminal (`Envio.status = FALHOU`, nunca reverte `CampaignRecipient` já `FALHOU`), incrementa `Session.failures` e envia para a fila `queue:dead-letter`; idempotente.
- **`SendMessageWorker`** (`send-message.worker.ts`, consumidor): 1 `Worker` BullMQ por sessão (concorrência 1, mesmo mapa por-sessão do produtor), criado sob demanda via `ensureWorker(sessionId)` (idempotente). Escuta o evento `failed`: só chama `finalizeFailure` quando `job.attemptsMade` atinge o `attempts` efetivo do job (`SEND_MAX_ATTEMPTS`, padrão 5, backoff exponencial com base `SEND_BACKOFF_DELAY_MS`, padrão 10s) — falha intermediária não vira transição terminal. Fora de escopo, deliberadamente: reconciliação automática de workers para sessões com jobs pendentes em Redis após o processo reiniciar (mesma decisão já documentada em `SessionService` para não retomar sessões WhatsApp sozinho).
- **`DeadLetterQueueService`** (`dead-letter.queue.ts`): fila única `queue:dead-letter`, sem worker consumidor — o Postgres (`Envio.status = FALHOU` + `failureReason`) já é a fonte de verdade; esta fila é só uma trilha operacional em Redis para investigar padrões de falha (ex.: muitos definitivos no mesmo DDD), sem reprocessar nada automaticamente.
- **Wiring** (`sending.module.ts`): agrupa produtor + consumidor + políticas (`TimezoneService`/`AntiBanService`) + dead-letter, mesmo padrão de módulo único de `ContactsModule`/etapa 13. `CampaignsService.createCampaign` (`campaigns.service.ts`) chama `enqueueCampaign`/`ensureWorker` só depois que a transação de persistência da etapa 14 commitou. `SendingModule` e `CampaignsModule` dependem um do outro (`PersonalizationService`/`MEDIA_STORAGE_PROVIDER` de um lado, `SendMessageQueueService`/`SendMessageWorker` do outro) — ciclo de **módulos** genuíno, resolvido com `forwardRef(() => X)` nos `imports` de ambos (nenhum provider injeta diretamente algo que volte a injetar ele mesmo, então não precisa de `forwardRef` no nível de construtor).

## Etapa 16 — Planos e uso

- **Por que RevenueCat, não Stripe/Mercado Pago direto**: iOS (App Store Guideline 3.1.1) e Android (Play Billing policy) exigem compra nativa via SDK da própria loja para desbloquear funcionalidade dentro do app — este backend nunca processa cartão nem inicia cobrança, só reflete o estado que a RevenueCat já reconciliou entre as duas lojas. `PlansController`/`PlansService` são deliberadamente passivos: quem "compra" é o app, via SDK; o backend só sincroniza o resultado.
- **Modelos** (`prisma/schema.prisma`): `Plan` (catálogo estático — `basico`/`pro`/`premium`, `revenueCatProductId` mapeia para o produto configurado no dashboard da RevenueCat), `Subscription` (1:1 por usuário, enum `SubscriptionStatus`: `ATIVA`/`TRIAL`/`EXPIRADA`), `PaymentHistoryEntry` (enum `PaymentStatus`: `PAGO`/`PENDENTE`/`FALHOU`), `RevenueCatEvent` (chave de idempotência do webhook — `id` é o próprio id do evento da RevenueCat). RLS em `prisma/rls/005_plans_rls.sql`, mesmo procedimento manual das etapas 11-14:
  ```bash
  npx prisma db execute --file prisma/rls/005_plans_rls.sql --schema prisma/schema.prisma
  ```
  Três exceções de RLS nesta etapa, cada uma por um motivo diferente (documentadas em `schema.prisma`): `Plan` não tem RLS porque é catálogo compartilhado por todos os tenants, nunca escrito por request de usuário (motivo oposto ao de `User` na etapa 10, que é isento por *preceder* o tenant). `Subscription`/`PaymentHistoryEntry` têm RLS de verdade, mas escrito a partir do webhook — sem JWT/request de usuário — via `PrismaService.withTenantContext(appUserId, ...)`, usando o `app_user_id` do próprio payload como tenant. `RevenueCatEvent` não tem RLS: é registro técnico interno (não é dado de negócio que algum endpoint autenticado devolve), verificado e escrito pelo `RevenueCatWebhookService` antes mesmo de se confirmar que o `app_user_id` corresponde a um usuário real.
- **`RevenueCatApiService`** (`revenuecat-api.service.ts`): único cliente REST da RevenueCat (`GET /v1/subscribers/{app_user_id}`, `fetch` global do Node, sem trazer `axios` para 1 endpoint). Chamado só por `PlansService.syncFromRevenueCat` — nunca no caminho do webhook, para não acoplar a velocidade de processar um evento à disponibilidade da API deles.
- **`RevenueCatWebhookService`** (`revenuecat-webhook.service.ts`), `POST /plans/webhook/revenuecat` (rota pública, chamada pela RevenueCat):
  - **Verificação de autenticidade**: `REVENUECAT_WEBHOOK_AUTH_HEADER` checa o header `Authorization` de forma exata (configurado do lado da RevenueCat, dashboard → Integrations → Webhooks); sem essa env, deliberadamente permissivo (dev local). `REVENUECAT_WEBHOOK_HMAC_SECRET` liga uma verificação mais forte e opcional: HMAC-SHA256 sobre os bytes **crus** do corpo (por isso `main.ts` sobe o Nest com `rawBody: true`), no formato `X-RevenueCat-Webhook-Signature: t=<timestamp>,v1=<hex>`, com tolerância de 5 minutos contra replay.
  - **Idempotência**: `RevenueCatEvent.id` é chave primária — reentrega do mesmo evento (a RevenueCat reenvia até 5x se não receber 200) vira `P2002` no `create`, tratado como no-op silencioso, nunca reprocessado.
  - **Tradução evento → estado**: eventos "ativadores" (`INITIAL_PURCHASE`/`RENEWAL`/`UNCANCELLATION`/`PRODUCT_CHANGE`/`SUBSCRIPTION_EXTENDED`/`TRANSFER`/`REFUND_REVERSED`) marcam `Subscription.status = TRIAL` (se `period_type: 'TRIAL'`) ou `ATIVA`; `CANCELLATION` só desliga `autoRenew` (a assinatura continua válida até `currentPeriodEnd` — a loja só efetiva no fim do período já pago); `EXPIRATION` marca `EXPIRADA`. Eventos financeiros (`INITIAL_PURCHASE`/`RENEWAL`/`PRODUCT_CHANGE`/`REFUND_REVERSED` → `PAGO`, `BILLING_ISSUE` → `FALHOU`) também geram 1 `PaymentHistoryEntry`.
  - **Nunca lança por evento/produto desconhecido**: tipo de evento que este backend não interpreta ou `product_id` fora do catálogo (seed desatualizado) só logam warning e seguem — evita retry infinito de um 5xx que nunca vai se resolver. `app_user_id` que não corresponde a nenhum `User` (FK falha, `P2003`/`P2025`) é tratado do mesmo jeito, silenciosamente.
- **`PlansService`** (`plans.service.ts`): `getCurrentPlan`/`getAvailablePlans` (marca `isCurrent`)/`getPaymentHistory` espelham `PlanRepository` do front. `syncFromRevenueCat` é chamado por `POST /plans/sync` logo após o app completar uma compra nativa via SDK — evita esperar o webhook (que pode levar de segundos a ~1min); busca o estado canônico via `RevenueCatApiService` e aplica a mesma tradução de status do webhook, adaptada ao formato da resposta REST (entre as assinaturas retornadas, escolhe a de `expires_date` mais distante no futuro; sem nenhuma ativa, cai para a de `expires_date` mais recente entre as expiradas — resulta em `EXPIRADA`, mas com o plano histórico correto associado, não "nenhum plano"). **Divergência deliberada do mock**: o `changePlan(planId)` do front mock troca de plano direto; aqui não existe essa rota — trocar de plano é sempre uma compra nativa nova via SDK, nunca uma chamada de API deste backend (ver comentário em `dto/plan-option.dto.ts`).
- **Bloqueio de novos envios por limite de uso**: `PlansService.assertWithinUsageLimit(tx, userId, quantity)` é chamado por `CampaignsService.createCampaign` **dentro da mesma transação** que persiste `Envio`s (`campaigns.service.ts`) — nunca numa transação separada, para que check e incremento de `Subscription.messagesUsed` sejam atômicos com a criação: se o limite estourar, a transação inteira (campanha, mensagens, mídia, destinatários) faz rollback, nenhuma campanha parcial fica salva. Usuário sem `Subscription`, ou com `status = EXPIRADA`, é tratado uniformemente como "sem plano usável" — não existe tier grátis separado. O incremento usa compare-and-swap (`updateMany` com `messagesUsed` atual na cláusula `where`) para não permitir duas campanhas concorrentes estourarem o limite juntas mesmo sob `READ COMMITTED`.
- **Rotas** (`plans.controller.ts`): `GET /plans/current`, `GET /plans/available`, `GET /plans/payment-history`, `POST /plans/sync` (as 4 atrás de `JwtAuthGuard`) e `POST /plans/webhook/revenuecat` (pública, protegida só pela verificação do `RevenueCatWebhookService`).
- **Env vars** (`.env.example`, `env.validation.ts`, todas opcionais no Joi — cada uma falha com causa clara em runtime se faltar na hora certa, não na subida do processo): `REVENUECAT_SECRET_API_KEY` (dashboard RevenueCat → Project Settings → API Keys → "Secret API Key"), `REVENUECAT_WEBHOOK_AUTH_HEADER`, `REVENUECAT_WEBHOOK_HMAC_SECRET`.

## Etapa 17 — Observabilidade avançada

- **Escopo**: fecha o §17 do README raiz — tempo real (WebSocket, etapa 11) e logs estruturados (nestjs-pino, desde a etapa 1) já existiam; esta etapa adiciona o que faltava: métricas Prometheus/Grafana, alertas operacionais proativos e confirma o Sentry (que na prática já estava ligado desde o `AllExceptionsFilter` original — nenhum código novo precisou ser escrito para ele, só verificado). Nenhuma tela nova do front consome isto diretamente: são rotas/infra para operação (dashboards, alertas, on-call), e uma tela de configurações (`GET/PATCH /settings`) que já existia como mock no front e ganha backend real aqui.
- **Modelo `UserSettings`** (`prisma/schema.prisma`): 1:1 por usuário (`notificationsEnabled`/`soundEnabled`, ambos default `true`), espelhando exatamente o `AppSettings` do repositório mock do front. RLS em `prisma/rls/006_user_settings_rls.sql`, mesmo procedimento manual das etapas anteriores:
  ```bash
  npx prisma db execute --file prisma/rls/006_user_settings_rls.sql --schema prisma/schema.prisma
  ```
- **`SettingsService`** (`settings.service.ts`): `getSettings`/`updateSettings` são o mesmo `upsert` por baixo — primeiro acesso de um usuário sem linha ainda cria com os defaults do schema (`update: {}` é no-op se a linha já existe, `create: { userId }` deixa o Postgres aplicar os defaults); `updateSettings` faz o mesmo upsert passando os valores recebidos tanto em `update` quanto em `create`, para o primeiro PATCH de um usuário novo já gravar o valor pedido em vez do default.
- **`AppInfoService`** (`app-info.service.ts`): `serviceStatus` deriva dos mesmos 2 checks de `HealthService.check()` (nunca reimplementados aqui) — 0 checks down → `OPERACIONAL`, 1 → `DEGRADADO`, 2 → `FORA_DO_AR`. `version` usa `APP_VERSION` do env se setado (útil pra sobrescrever em runtime no Railway sem rebuild), senão cai no `version` de `package.json`.
- **Rotas** (`settings.controller.ts`, todas atrás de `JwtAuthGuard` exceto nenhuma — as 3 exigem usuário autenticado): `GET /settings`, `PATCH /settings`, `GET /app-info`.
- **`MetricsService`** (`metrics.service.ts`, via `prom-client`): usa um `Registry` próprio por instância (não o registry global default do `prom-client`) — evita poluição entre testes e deixa explícito que só este serviço é dono das métricas. Expõe `zabot_messages_sent_total`/`zabot_messages_failed_total` (`Counter`), `zabot_message_send_latency_seconds` (`Histogram`, buckets de 0.5s a 5min — cobre desde envio rápido até fila congestionada), `zabot_sessions_by_status` (`Gauge` com label `status`) mais as métricas de processo padrão do Node (`collectDefaultMetrics`, prefixo `zabot_process_`). `recordMessageSent`/`recordMessageFailed` são chamados por `SendMessageProcessorService` (`markSent` e `finalizeFailure`, respectivamente — falha de tentativa intermediária não conta, só a transição terminal); `recordSessionStatus` é chamado por `SessionGateway.emitSessionEvent`, o único ponto que já centralizava toda mudança de status de sessão para o WebSocket, reaproveitado aqui para o gauge. O gauge rastreia o último status conhecido por usuário (`Map` interna) para decrementar o status anterior e incrementar o novo só quando há mudança de verdade (idempotente contra a mesma notificação repetida).
- **`GET /metrics`** (`metrics.controller.ts`): formato texto Prometheus (`Content-Type: text/plain; version=0.0.4`), protegido por `MetricsAuthGuard` — se `METRICS_TOKEN` não estiver setado no env, a rota fica aberta (dev local); se estiver, exige `Authorization: Bearer <token>` exato.
- **`AlertsService`** (`alerts.service.ts`): mesmo padrão de job periódico da `SessionService` (etapa 11) — `setInterval` armado em `OnModuleInit`, limpo em `OnModuleDestroy`, nunca `@nestjs/schedule` (não é dependência deste projeto). Roda 3 verificações independentes a cada ciclo (`ALERTS_CHECK_INTERVAL_MS`, padrão 60s), cada uma varrendo todos os usuários via `prisma.user.findMany()` (tabela isenta de RLS, igual à etapa 16) e depois abrindo `prisma.withTenantContext(userId, ...)` por usuário — único jeito sancionado de operação "todos os usuários" sem contornar RLS: (1) **sessão caída** — status diferente de `DESCONECTADA` (usuário não pediu pra desconectar) mas sem heartbeat de worker há mais de `ALERT_SESSION_DOWN_MINUTES` (padrão 10min); (2) **fila travada** — `Envio`s em `PENDENTE` há mais de `ALERT_STUCK_QUEUE_MINUTES` (padrão 15min) sem transicionar; (3) **taxa de falha** — `FALHOU`/(`ENVIADO`+`FALHOU`) acima de `ALERT_FAILURE_RATE_THRESHOLD` (padrão 30%) na janela `ALERT_FAILURE_RATE_WINDOW_MINUTES` (padrão 30min), só dispara com amostra mínima (`ALERT_FAILURE_RATE_MIN_SAMPLES`, padrão 10 — evita alerta com 1 falha em 1 envio). Cada alerta tem uma chave própria (ex.: `session_down:<userId>`) com cooldown (`ALERTS_COOLDOWN_MS`, padrão 30min) guardado num `Map` em memória, pra não repetir o mesmo alerta a cada ciclo enquanto o problema persiste. Disparo em 3 camadas independentes, cada uma isolada de falha na outra: log estruturado (`logger.warn`, sempre), Sentry (`Sentry.captureMessage`, só se `SENTRY_DSN` estiver setado), e e-mail (`EMAIL_PROVIDER` da etapa 3, só se `ALERT_EMAIL_TO` estiver setado — falha de envio de e-mail é capturada e logada, nunca derruba o ciclo de verificação).
- **Sentry**: já capturava toda exceção 5xx desde o `AllExceptionsFilter` original (etapas iniciais) — confirmado nesta etapa sem necessidade de código novo; `AlertsService` reaproveita o mesmo `SENTRY_DSN` para reportar alertas operacionais (não-exceções) como mensagens de warning.
- **Env vars** (`.env.example`, `env.validation.ts`, todas opcionais): `APP_VERSION`, `METRICS_TOKEN`, `ALERT_EMAIL_TO`, `ALERTS_CHECK_INTERVAL_MS`, `ALERTS_COOLDOWN_MS`, `ALERT_SESSION_DOWN_MINUTES`, `ALERT_STUCK_QUEUE_MINUTES`, `ALERT_FAILURE_RATE_THRESHOLD`, `ALERT_FAILURE_RATE_WINDOW_MINUTES`, `ALERT_FAILURE_RATE_MIN_SAMPLES`.
- **Wiring** (`metrics.module.ts`): `@Global()` igual ao `EmailModule` — `MetricsService` fica injetável em qualquer módulo (`SendingModule`, `WhatsAppModule`) sem reimportar `MetricsModule`, bastando estar em `AppModule.imports`. `AlertsService` mora no mesmo módulo (não um `AlertsModule` separado) por ser o mesmo domínio de observabilidade e não precisar ser injetado em nenhum outro lugar — só liga o próprio timer interno via `OnModuleInit`.

## Etapa 18 — Ajustes finos de segurança e preparação para produção

O que já existia desde etapas anteriores e não precisou de mudança: rate limiting global + por rota sensível (`ThrottlerModule`/`@Throttle`, etapa 10), redação de segredos no log (`req.headers.authorization`/`cookie`, `*.password`/`*.token`/`*.accessToken`/`*.refreshToken` — `logging.module.ts`), validação de env na subida (`env.validation.ts`, Joi), criptografia em repouso do auth state (`SessionCryptoService`), verificação HMAC do webhook RevenueCat. O que foi adicionado nesta etapa:

- **`helmet`** (`main.ts`): headers de segurança padrão (HSTS, `X-Content-Type-Options`, `X-Frame-Options` etc.) em toda resposta.
- **CORS travado por env** (`main.ts` + `CORS_ORIGIN`, ver `env.validation.ts`/`.env.example`): antes, `origin: true` refletia **qualquer** origem com `credentials: true` — combinação perigosa (qualquer site conseguiria ler resposta autenticada via navegador). Agora só as origens listadas em `CORS_ORIGIN` (separadas por vírgula) recebem `Access-Control-Allow-Origin`; sem a env, nenhuma origem cross-site é autorizada. O app Flutter nativo não passa por CORS (mecanismo só existe em navegador), então não é afetado de nenhuma forma.
- **`trust proxy`** (`main.ts`): o Express agora confia no `X-Forwarded-For` do proxy reverso do Railway — sem isso, o `ThrottlerGuard` contava rate limit pelo IP do proxy (um só, compartilhado por todo mundo) em vez do IP real de cada cliente.
- **Rate limit no webhook público** (`plans.controller.ts`): `POST /plans/webhook/revenuecat` não tinha `@Throttle` próprio (única rota pública do backend) — agora limitada a 30 req/min.

**Checklist antes de ir para produção de verdade:**

1. **Secrets**: gerar `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET` (32+ caracteres aleatórios) e `SESSION_ENCRYPTION_KEY` (`openssl rand -hex 32`) únicos de produção — nunca reaproveitar os de dev/CI. Guardar só nas variáveis de ambiente do Railway, nunca commitados.
2. **`CORS_ORIGIN`**: setar só se existir cliente web/admin de verdade; deixar vazio caso contrário (o app mobile não precisa).
3. **`REVENUECAT_WEBHOOK_AUTH_HEADER`** e, idealmente, **`REVENUECAT_WEBHOOK_HMAC_SECRET`**: sem a primeira, o endpoint de webhook aceita qualquer payload sem checar origem.
4. **`METRICS_TOKEN`**: setar em produção — sem ele, `GET /metrics` fica aberto publicamente (não vaza dado de usuário, mas é informação operacional interna).
5. **`SENTRY_DSN`** e **`ALERT_EMAIL_TO`**: preencher para observar erros/alertas de produção em tempo real (etapa 17).
6. **HTTPS**: garantir que o domínio público do Railway (ou domínio próprio) sirva só HTTPS — o `helmet()` adicionado aqui já manda `Strict-Transport-Security`, mas isso só tem efeito se a conexão já for HTTPS na origem.
7. **Migrations + RLS**: rodar `npx prisma migrate deploy` e todos os `prisma/rls/*.sql` contra o banco de produção antes do primeiro deploy (mesmos passos do CI, seção acima) — sem RLS aplicado, toda rota que usa `withTenantContext` falha.
8. **Backups do Postgres**: configurar backup automático (Railway tem backup gerenciado para o plugin Postgres) — nenhuma rotina de backup é feita pelo próprio backend.
9. **`npm install`**: gerar/commitar um `package-lock.json` de produção antes do primeiro deploy real (`helmet` foi adicionado ao `package.json` nesta etapa) e rodar `npm ci` no pipeline de build, não `npm install`.
10. **Réplicas**: se o Railway escalar a API para múltiplas réplicas, trocar o storage do `ThrottlerModule` (em memória, hoje) por um backing Redis compartilhado, e o adapter do `SessionGateway` (socket.io, em memória) por `@socket.io/redis-adapter` — ambos documentados como limitação de 1 réplica nas etapas 10/11.
